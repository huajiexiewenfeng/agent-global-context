# Agent Global Context 高覆盖采集优化设计

> 日期：2026-08-13
> 状态：已确认，待实现计划
> 范围：提高 Codex 任务记忆采集率并自动分类；不修改普通 Recall，不引入 Trace/Eval Loop

## 1. 结论

AGC 当前最需要优化的不是 Recall 权重，而是记忆采集入口。

本次采用：

> **所有任务都检查，原子记忆尽量采集，分类自动完成，正式记忆稳健晋升，普通 Recall 继续克制。**

具体做法：

- 首次回填最近 7 天的已完成 Codex 任务。
- 此后持续处理每一个新完成或继续更新的 Codex 任务。
- 每个任务提取 0–8 条原子观察。
- 每个任务都生成采集回执，即使最终提取结果为 0。
- 观察先进入高覆盖采集层，再聚合为候选或正式记忆。
- 采集层默认不进入普通 Prompt，记忆增加不等于噪声增加。

## 2. 当前问题

### 2.1 数据明显不足

截至 2026-08-13：

- 正式记忆只有 23 条。
- 候选记忆只有 1 条。
- 最近一周只新增了 1 条正式记忆。

用户的大部分工作、学习和研究都在 Codex 中完成，实际产生的信息远多于当前记忆数量。

### 2.2 根因是采集没有稳定运行

当前 `agc.write` 已经能够写 Candidate 和正式记忆，但 Capture 依赖主任务 LLM 主动想起并调用。

系统没有稳定的 Codex 任务完成触发点，也没有覆盖全部任务的增量扫描。因此无法区分：

- 任务中确实没有值得保存的信息。
- 任务有价值，但 Capture 没有运行。
- Capture 运行了，但失败或超出预算。

### 2.3 入口过早追求高精度

当前系统在信息进入存储前就要求它足够稳定、长期且有用。这适合正式记忆，却不适合记忆库仍然非常稀疏的阶段。

没有足够样本，系统也无法通过真实使用判断：

- 哪类项目记忆最有价值。
- 哪类学习记录能够帮助成长。
- 哪些普通观察会在后续任务中发挥作用。
- 哪些内容只是一次性噪声。

### 2.4 Candidate 不适合作为大规模采集库

现有 Candidate 主要服务证据积累和正式晋升，只保存简短结论、分类和来源。

如果把所有任务观察都直接写入 Candidate，会混淆两种职责：

- “任务中出现过什么”——高覆盖观察。
- “什么可能值得长期相信”——待晋升结论。

因此需要在 Candidate 前增加独立的采集观察层。

### 2.5 项目和学习覆盖不足

当前记忆偏重身份、偏好、原则和少量项目事实，以下信息明显不足：

- 项目目标、角色、关键决策、阶段成果和可复用流程。
- 学习主题、认知突破、误区修正、能力证据和下一步。
- 研究方向、假设、实验、判断变化和开放问题。
- 跨项目重复出现的工作方法与成长信号。

## 3. 目标与边界

### 3.1 目标

1. 所有已完成 Codex 任务都经过一次旁路采集检查。
2. 尽量保留可分类的原子观察，不在入口过度过滤。
3. 用户可以按项目、学习、研究等分类查看系统采集了什么。
4. 自动去重、聚合和晋升，尽量减少人工参与。
5. Capture 失败或延后不影响原任务。
6. 普通 Recall 继续只读取少量相关正式记忆。

### 3.2 不做什么

- 不扫描全部数百个历史长对话。
- 不保存完整会话、代码、Diff、终端日志或思维链。
- 不把所有观察直接变成正式记忆。
- 不引入向量数据库、Trace Runtime 或 Eval Runtime。
- 不用 AGC 替代项目本地 LLM Wiki。
- 不放宽 sensitive 和 secret 的禁止持久化边界。

## 4. 方案比较

### 方案 A：全部直接写正式记忆

正式记忆增长最快，但重复、冲突、过期内容和 Recall 噪声也会快速增加，后续清理成本高。

结论：不采用。

### 方案 B：高覆盖采集层 → Candidate → 正式记忆

所有任务都检查，尽量留下原子观察；通过分类、聚合和真实使用判断价值。普通 Recall 仍只读取正式记忆。

优点是同时提高采集率与保持 Prompt 安静；代价是需要水位、回执和采集层查询。

结论：采用。

### 方案 C：只采集显式重要任务

Token 最少，但仍依赖 LLM 提前判断任务是否重要，普通任务中意外出现的高价值信息会继续漏掉。

结论：不采用。

## 5. 选定设计

### 5.1 四个层次

| 层次 | 作用 | 是否参加普通 Recall |
|---|---|---|
| Capture Receipt | 证明某个任务 revision 是否处理成功 | 否 |
| Collected Observation | 保存任务中提取出的原子观察 | 否 |
| Candidate | 聚合多条观察，表达待验证的长期结论 | 否 |
| Formal Memory | 保存稳定、明确、可使用的长期记忆 | 是 |

Capture Receipt 不保存语义正文，只记录任务、revision、状态、数量和 Token。

Collected Observation 必须包含短内容、分类、时间、项目范围和来源，但不保存 Task Capsule 或完整对话。

Candidate 继续使用现有行为证据门槛：至少 3 条证据、2 个独立任务和 7 天时间跨度。达到门槛只表示可以由 LLM 裁决，不由 Runtime 自动发明长期结论。

### 5.2 采集流程

```text
发现已完成或产生新 revision 的 Codex 任务
  → 检查水位与 Receipt
  → 构建紧凑 Task Capsule
  → LLM 提取 0–8 条原子观察
  → 敏感信息门禁
  → 自动分类并写入 Collected Observation
  → 与已有 Observation、Candidate、Memory 聚合
  → ignore / reinforce / update / candidate / formal
  → 写 Receipt 并推进水位
```

LLM 负责语义提取、分类、相似性判断和晋升建议。Runtime 负责 Schema、来源幂等、安全门禁、原子写入、状态迁移、水位和回执。

Capture 由旁路 Runner 执行，不要求主任务在输出最终答案前完成。没有可靠完成事件时，Runner 周期性扫描 Codex 任务索引，并通过 revision 和水位保证最终覆盖。

## 6. 分类整理

每条观察先归入一个主分类，再使用现有 `kind` 与 scope 描述其语义和适用范围。

| 主分类 | 优先采集内容 |
|---|---|
| Project | 项目关系、目标、里程碑、决策、成果、约束、可复用流程、问题解决模式 |
| Learning | 学习主题、新理解、误区修正、能力证据、学习成果、开放问题、下一步 |
| Research | 研究方向、假设、实验、技术判断、发现、判断变化、开放问题 |
| Work | 职责、工作流、协作方式、交付成果、可复用方法、长期约束 |
| Personal Growth | 目标、兴趣、偏好、原则、背景变化、绑定具体领域的成长信号 |

以下内容默认不生成观察：

- 普通代码细节。
- 临时日志和一次性命令。
- 仅当前任务有效的操作说明。
- 关于第三方的普通信息。
- 没有任务证据的人格、动机和心理推断。

它们只有形成决策、成果、稳定约束或可复用方法时，才进入采集层。

## 7. 历史回填与持续增量

### 7.1 首次回填

- 只处理执行时刻向前最近 7 天的已完成任务。
- 从最新任务向前处理。
- 每任务提取 0–8 条原子观察。
- 总模型输入与输出预算不超过 100,000 Token。
- 达到预算后停止，并把未处理任务记录为 `deferred_budget`。
- 如果样本仍不足，再由用户授权按 7 天一个批次向前扩展。

### 7.2 持续增量

- 首次回填后记录处理水位。
- 每个新完成任务都进入采集范围。
- 已处理任务继续对话并产生新 revision 时再次处理。
- 相同来源 revision 严格幂等，不重复采集。
- 处理可以延后，但不能无 Receipt 地丢失。

## 8. Token 与主任务隔离

每个任务先生成目标上限约 1,200 Token 的 Task Capsule，只保留：

- 标题、时间和项目范围。
- 用户明确表达的高信号片段。
- 最终结论中的决策、成果和下一步。
- 必要的来源定位。

如果某条观察明显具有长期价值但证据不足，只允许一次最多约 3,000 Token 的局部证据读取，不读取完整长对话。

Capture 始终遵守：

- 不改变原任务 Prompt。
- 不阻塞最终答案。
- 不触发原任务重试。
- 单任务失败不影响同批其他任务。
- 预算不足、失败与隔离状态都必须如实记录。

## 9. 聚合与正式化

以下内容可以自动成为正式记忆：

- 用户直接明确表达的持久目标、兴趣、偏好、原则和背景事实。
- 来源明确且已验证的项目成果、关键决策或可复用运行手册。
- 满足证据门槛，且由 LLM 判断语义稳定的领域能力或行为模式。

以下内容保留在 Observation/Candidate，或等待裁决：

- 单次任务中的弱推断。
- 证据不足的能力或成长结论。
- 无法判断是新记忆还是更新的内容。
- 高影响冲突。

项目观察必须保留项目 scope。只有跨项目重复出现后，才可以抽象为个人工作方式或能力。

## 10. 查看与评估

用户必须能看到正式记忆之外的采集结果。第一版提供只读的采集概览与分类搜索，支持按以下维度查看：

- 时间。
- 项目。
- 主分类和子类型。
- kind、scope 和处理状态。

普通 Recall 不读取采集层。采集概览只用于用户主动查看、定期 AGC 复盘以及聚合晋升。

每次复盘至少报告：

- 采集范围内任务数和 Receipt 覆盖率。
- 产生观察的任务数。
- 观察数量及分类分布。
- 聚合、强化、新增正式记忆和忽略数量。
- Token 使用、失败和延后任务。

## 11. 验收标准

1. 最近 7 天回填范围内，每个可识别的已完成 task revision 都有 Receipt。
2. 建立水位后，每个新完成或更新的 task revision 最终都有 Receipt。
3. 每任务保存 0–8 条带来源、分类、时间和 scope 的原子观察。
4. 项目、学习、研究、工作和个人成长可以独立统计和查看。
5. 完整会话、思维链、长代码、Diff 和日志不进入 AGC 存储。
6. Collected Observation 默认不进入普通 Prompt。
7. Capture 失败不改变原 Codex 任务结果。
8. 重复执行不会重复创建同一来源 revision 的观察和 Receipt。
9. 首次回填遵守 100,000 Token 总预算。
10. 用户可以从采集层看到足够样本，再判断哪些记忆真正有用。

## 12. 成功判断

第一阶段不以正式记忆数量为唯一指标，而是先回答：

1. 每个任务是否真的被检查过？
2. 系统到底采集到了哪些类别的记忆？
3. 用户能否看到这些记忆并判断其价值？

当高覆盖采集稳定运行并积累足够样本后，再依据真实数据调整各分类的采集权重、聚合规则、正式化条件和 Recall 价值。
