日期：2026-10-03

状态：2026-10-04 按已批准边界完成本地开发、隔离测试、新旧对照及独立审查，采用 24 小时全量校验有效期。未提交、推送或安装，未进行生产验收。

实施计划：[增量 Capture](../plans/2026-10-04-agc-incremental-capture.md)。改造前基线为 `206e5b864336fc7472c70bab459737dc13c35faf`；新旧对照在 `D:\tmp_test` 使用相同合成输入，不回退生产安装。

关联：`agc-capture-reliability-closeout`；[当前诊断](../../../.llm-wiki/bugs/2026-09-23-capture-system-proxy-timeout.md)。

## 1. 要解决的问题与证据边界

自动周期在调用模型前反复读取历史数据：Scanner 和 Runner 均执行全量恢复；Source discovery 不利用 hint 缩小解析范围；Runner 读取多次完整快照。

本轮现场采样显示前六分钟仍在恢复或 Source discovery。合成的十条健康完成记录在一次恢复中触发五十次文件读取、只有三十个不同路径，且没有需要修复的事务。这证明重复本地 I/O 存在，不证明它解释所有超时，也不是模型兼容性结论。

目标是减少正常周期中与历史规模相关的重复内容读取。首次建基线、全量校验、目录元数据检查、索引加载仍有成本；不宣称整个流程变成 O(新增条数)，不承诺未经测试的倍数或分钟数。

## 2. 方案选择

| 方案 | 收益 | 局限 | 决定 |
|---|---|---|---|
| 继续扩大并行读取或超时 | 局部实现简单 | 仍反复做历史全量工作，不能解决规模增长 | 不选 |
| 增量调度加独立全量校验 | 将日常采集与历史完整性检查解耦 | 必须维护可重建状态，明确历史损坏的发现时效 | 推荐，用户已同意此方向 |
| 全面迁移数据库或常驻服务 | 可进一步改变存储与调度 | 超出本次最小修复范围，迁移和回滚成本更高 | 不选 |

## 3. 不变的边界

- 只在 AGC 仓库现有分支开发；不改 `agent-runtime-modules`。
- 不删除、压缩或重写历史 Session、Census、正式记忆和 Trace DB。
- 保持现有七天 discovery 窗口、候选资格、任务间排序、`max-items`、预算、重试和不自动晋升规则。
- 不把 delta 列表冒充完整 Census；不让增量扫描使已知待处理 revision 丢出当前合法候选集合。
- Capture 保留当前配置的 `gpt-6.1-sol`；独立审查任务的模型不在本次范围。
- 不延长周期超时，不创建第二个 Capture Runner，不提高模型调用并发。
- 复用原生锁、租约、fencing 和提交原子性，不删除或绕过写锁。
- 本次不改 Recall、人工回填授权协议、记忆审查流程、Eval/Judge 或报表产品功能。

## 4. 日常路径

### 4.1 增量发现

为已扫描文件保留可重建的元数据状态，不保存原始消息或 Capsule。只对新增、变化、未稳定完成、dirty 标记命中或缺少可信扫描状态的文件重新解析。

仍需发现文件集合变化。不能只检查新日期目录，也不能仅按 mtime 跳过旧会话。文件身份、大小、高精度时间等只用于判断是否需要重新扫描，不作为真实性或发送授权证明。替换、截断、归档移动、版本变化、异常状态都必须失效并重查。

稳定文件的已知 revision 元数据参与现有窗口计算；窗口推进不能使缓存的过期 revision 成为新候选。扫描推进点只能在对应 Census 和 receipt 记账完成后发布；进程中断后允许重放，不允许漏账。

局限必须明示：外部改写若保留所有可观察元数据，可能要到强制全量 Source 扫描或该记录的 Capsule 加载时才被发现。本次独立历史完整性审计验证持久化 Source 扫描状态，不重新读取全部原始 Session 正文，不能将其描述为每 24 小时重新核验全部源正文。真正进入 Capsule 的源内容仍由现有加载器重新检查。

### 4.2 未完成事务恢复

将完整历史审计与本轮事务恢复分离。日常路径恢复未完成或中断的事务，不再为了恢复一条事务验证所有健康完成记录的 manifest 和 observation。

不能直接采用“journals 为空就跳过恢复”：当前 `begin_extraction()` 在写 `extracting` 时尚未建立 extraction commit journal。实现必须覆盖该崩溃窗口，并让恢复集合在事务写入前可追踪，结束后才撤销。

有效租约、未知或冲突事务仍按保守规则处理；遗留根或不能证明恢复集合完整的状态不得静默跳过恢复。

历史 orphan 检查不放进每轮采集；全量校验只报告此类问题，不新增自动删除历史数据的行为。已有事务中可证明归属的临时提交清理维持原有契约。

### 4.3 Runner 只获取调度必需的信息

避免为选取有限候选重复调用完整 `read_snapshot()`。增量状态只提供待处理线索；不能成为 Receipt、Ledger、Census 或正式记忆的第二份事实来源。

选中记录必须从当前持久化事实重新校验。发送前和提交前保持当前源身份、revision 完成状态、排除/Forget、隔离、租约、预算、Capsule 与持久化安全边界，不凭缓存放行。

完整读服务、人工回填、审查和备份校验保留现有行为，不能把轻量调度视图冒充完整健康快照。

## 5. 独立全量校验与首次启用

首次启用增量路径需要单独完成基线校验并原子发布可重建状态；不在每个普通周期反复冷启动重建。独立入口不调用模型，不自动写正式记忆，不新增自动清理历史数据行为。

全量校验覆盖历史 Census/Receipt/Ledger/Manifest/Observation 关系及 Source 扫描状态。完成凭据必须绑定输入代次；跨越并发修改的检查不得误报全量健康。与原有 Runner 互斥协调，不能取消锁来提速。

采用已确认的 24 小时全量检查结果有效期。到期且未完成新校验应显示 `audit_due`，不冒充全局健康；单纯逾期不增加自动停采门槛，本轮选中记录仍须通过当前安全检查。实际发现完整性错误时隔离受影响记录；无法界定影响范围时暂停相关发送。首次无有效基线或增量状态损坏仍不允许凭缓存发送。电脑关闭或校验失败可能使实际间隔超过 24 小时，因此这是状态有效期，不是无条件完成保证。

这会降低冷历史损坏发现的即时性，用户已确认该时间取舍。此稿不授权创建或修改生产计划任务；正式安装时再明确独立校验的维护窗口。

索引损坏、配置绑定或版本变化、恢复/Forget 操作必须使相关派生状态失效。硬忘记必须清除其中的目标标识或使整个派生状态在同一事务内不可用；恢复备份后必须重新建基线。新索引不能引入忘记残留或自动重抓。

## 6. 实施边界与顺序

1. 增量 Source 状态与等价性测试：复用现有路径和输入契约，不改七天 Census 语义。
2. 事务恢复集合、轻量 Runner 读取及全量校验入口：必须同时覆盖旧根初始化、崩溃窗口、Forget 和备份恢复失效。
3. 集成与新旧对照：确认热路径不再读取全部完成记录的内容；随后才制作可回滚安装包。

主要代码范围是 `codex_source_adapter.py`、`capture_scanner.py`、`capture_store.py`、`capture_runner.py`、`capture_cli.py` 及必要的小型状态模块。与 Forget/备份的修改只允许增加派生状态的清除或失效支持；不重构其主流程。

不是只去掉两次恢复调用。若索引一致性或兼容性必须引入数据库迁移、常驻服务、改写历史事实或修改外部 Runtime，应停止并重新讨论范围。

## 7. 验收

- 先用真实文件组成的合成数据写失败测试，再实现；所有临时数据放在 `D:\tmp_test`，不使用生产 Capsule 调模型。
- 同一冻结输入、同一时钟和配置，比较旧完整路径与新增量路径的 revision 集合、receipt 状态、候选资格、排序和账务结果；不能只比较最终数量。
- 验证新增、旧会话追加、截断、替换、归档移动、partial tail、dirty marker、窗口推进与跨扫描失败重放；未变化文件不重新解析正文。
- 在新增状态每个提交边界注入中断，验证无漏账、重复提交或遗留 `extracting`；有效租约不被当成死事务。
- 验证失效/损坏索引、隔离、排除、Forget、恢复备份和源身份变化均不能靠缓存放行模型发送；全量凭据单纯过期只标记待检查，不绕过逐项检查，也不额外造成自动停采。
- 验证完整审查/读取、人工回填、预算及备份/Forget 相关回归，范围随实际影响确定。
- 新旧性能比较采用等规模合成历史加固定增量，在相同环境分别记录冷启动和至少三次热运行：各阶段耗时、正文解析数、小文件读取数、锁占用和实际处理数。合成收益不得写成生产收益。
- 生产验收在安装后另记：至少两个连续、自然触发的自动周期在既有 deadline 内结束，确认实际模型、终态 Trace 和 receipt；无新增候选的周期只能证明空跑健康，不能证明提取能力。
- 现有健康指标若引用全量检查，应保留检查时间/范围，不以本轮增量成功替代全局完整性结论。

## 9. 新旧对照的方法说明

使用 `scripts/benchmark_incremental_cycle.py`，分别加载 Git 基线 `206e5b8` 的隔离副本与当前开发代码；不切换或覆盖生产版本。两次运行复用同一受控 Source 路径并重置为相同的合成 JSONL，Memory Root 分开且从空目录建立。固定时钟、配置、40 条已完成历史观察及四轮增量（2、1、1、1 条）；提取器是确定性的测试替身，不调用模型，不评价记忆语义质量。

| 记录项 | 计算口径与用途 | 限制 |
|---|---|---|
| 结果等价性 | 比较每轮完整 RevisionRef、Receipt、Observation、Ledger、已记账 key、增量预算快照、候选顺序及语义报告字段 | Runner 耗时是非确定字段，单独比较；新增审计状态字段单列，不混作旧版结果 |
| Source 正文解析次数 | 在被测 Scanner + Runner 期间计数 `_scan_file` 调用，包含选中 Capsule 必须执行的重新核验 | 不是字节数；仍枚举目录元数据，不代表零磁盘读取 |
| Capture JSON 读取次数 | 对现有 `read_json` 帮助函数及已加载引用计数成功读取，并按命名空间统计 | 不是全部 OS I/O；不含失败读取，未经过该函数的读取不计入 |
| 阶段与锁耗时 | 单调时钟分别测 Scanner、Runner、锁等待及持有时间；首次完整审计的 bootstrap 成本单列 | 合成小样本、OS 文件缓存未清空，不能外推生产速度或稳定性 |

历史种子通过不启用 Source 缓存的适配器写入；新版本显式完成一次健康 bootstrap 后再测量。第一轮为发现元数据冷启动，其后三轮为热运行，各轮仍有真实合成增量。每轮测量结束后才调用完整快照和预算校验，因此校验自身不计入热路径；任何完整性失败、实际提取/观察数量偏差或运行中代码变化均使该次实验失败。输出保留输入、实现、夹具及测量脚本的 SHA-256，便于确认可比性。

本实验只能证明指定合成负载下的输出等价与重复读取变化。历史规模扩大、真实模型耗时、生产锁竞争、自然触发和长时间稳定性仍需另外验收；不能把本表读数直接当成用户收益或生产超时已解决。
